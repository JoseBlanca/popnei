# Why the principal component analysis takes 0.801 s and not 0.3 s

22 September 2026. A performance review of the principal component
analysis of the variants, `do_pca_from_variants`, which the plan
`docs/plans/pca.md` built the same day and which misses the target of
"Speed" of `docs/specs/pca.md` by 2.7 times. It was asked for by the
owner when that plan reported the miss. The review reads code and
machine code and proposes experiments; it changes nothing by itself.
What it decides is which experiments are worth running and in which
order. The experiments themselves, and what each one gave, are at the
end, under "What the experiments showed", which is filled in as they
run.

The words this document uses. **The analysis** takes the genotypes of a
dataset and gives the few axes along which its individuals vary most.
Every variant becomes one number per individual, its **dosage**, how
many alleles of its genotype are not the most frequent allele of that
variant. To **standardize** a row is to turn the genotypes of one
variant into those dosages, with the mean of the variant taken off and
divided by its standard deviation. A **block** is the run of variants
that a reader gives at a time, here 5000 variants of 1000 individuals,
held as one array of one byte per allele. **G** is the individuals x
individuals matrix that the standardized blocks are multiplied into, and
whose eigenvectors give the result. A **pass** is one reading of the
whole dataset; the analysis makes two when it is asked for the weights
of the variants. **NEON** is the set of vector instructions of an Apple
processor, which work on 16 bytes or two `f64` at a time; a loop the
compiler turns into them is **vectorized**, and a **gather** is a read
from an address the data itself gives, which NEON cannot do.

## What was reviewed, and against what

The analysis at commit 21e31a3 of the branch `plan/pca`: the module
`pca` of the core crate, `crates/popnei-linalg`, the reader of the vars
file and the two binding layers. The review works on the branch
`perf/pca`, which starts there, so that `plan/pca` stays as the owner
was told it is.

The target is **0.3 s** for 100000 variants of 1000 individuals, on one
thread, with no weights. The analysis takes **0.801 s**. On the 18
threads of the machine it takes 0.352 s, and with the weights of 10
components, which is a second pass, 1.353 s. pyNei takes 8.106 s and
holds 5.59 GB where popnei holds 0.21 GB; plink2 takes 0.248 s from its
own file of genotypes held in 2 bits. In a browser the analysis takes
4.500 s against a target of 5 s, which is met, so this review is about
the native number. Every one of those figures was measured on the
owner's Apple M5 Pro on 22 September 2026 and is in
`docs/reports/pca-measurement.md` with the command that produces it
again.

Where the 0.801 s goes, from a sampling profile of 15373 samples in that
report:

| part of the analysis | share | time | per block |
|---|---|---|---|
| standardizing the rows of the blocks | 51.6 | 0.413 s | 20.6 ms |
| the product of each block with itself | 31.7 | 0.254 s | 12.7 ms |
| reading the vars file | 13.3 | 0.107 s | 5.3 ms |
| the eigendecomposition | 3.0 | 0.024 s | |
| the signs, the projections and the rest | 0.4 | 0.003 s | |

Nine categories were sent, one reviewer each: methodology, hot loops,
numbers, allocations, data layout, concurrency, the linear algebra and
wasm, input and output, and the Python boundary. None of them took a
wall time, so that they could run at once without measuring each other.

What was left out: the analysis of a table, `do_pca`, which is not on
this path; the sizes above 1000 individuals, where the ranking inverts
and the eigendecomposition dominates, which is said where it matters and
measured by nobody; and the browser, whose target is met.

## The verdict: apply

The profile is good enough to act on, and the first candidate has a
mechanism that was verified in machine code, a gain that is bounded
below by an instruction count, and a change that alters no result.

**The 0.413 s of standardizing is not a memory problem and not a
floating point problem. It is three scalar loops where the machine has
vector instructions.** Two reviewers counted the instructions of a row
of 1000 diploid individuals in the machine code of the release build,
and the two counts agree on which loops they are:

| pass over the row | instructions per row | share |
|---|---|---|
| writing the code of each genotype | 34000 | 54% |
| counting the alleles to find the major one | 21600 | 34% |
| looking each code up in its value | 3500 | 5.6% |
| sweeping the table of 128 allele counts | 1800 | 2.9% |
| counting the codes | 1700 | 2.7% |

The two loops that are 88% of a row are the two that the compiler left
scalar, and the reason is known for each. The loop the spec was written
to make vectorizable, the counting of the codes, is 2.7% and the
compiler did vectorize it. The gather that the measurement report
singled out is 5.6%, and the obvious replacement for it is worse, which
one reviewer compiled and measured in instructions.

The floating point arithmetic of a row is 21 operations against about
7000 on bytes and integers, so it is not where the time is. The working
set of a row is 14.6 KB against 128 KB of first level cache, so nothing
about the layout of a row will find the half second either.

## The measurement plan

In this order, because each unblocks what follows it.

1. **A benchmark that times the four passes over a row on their own.**
   No harness in the repository can: they are private functions, and
   the compiler inlines all four into one closure, so the profiler sees
   them as one frame and the split above is an instruction count and not
   a time. Without it every finding about the 0.413 s is a hypothesis
   that cannot be refuted. It reads one real block of `big.vars`, asserts
   it is 5000 x 1000, and prints the best of five for each pass and for
   the whole row, with a checksum so that nothing is optimized away.
2. **A build profile with debug information**, inheriting from release,
   so that a profile shows the inlined frames. It changes no code
   generation.
3. **The experiments on the code**, in the order of the findings below.
4. **The build configuration**, one setting at a time: link time
   optimization thin, then fat, then one code generation unit. The
   numbers reviewer checked that none of them can introduce a fused
   multiply and add or reassociate a sum, so they cannot move a result.
   `target-cpu=native` is not worth trying: it adds three features and
   the ones this code uses are already on.

Every wall time is taken with nothing else building, the best of five
runs, with `VECLIB_MAXIMUM_THREADS=1 RAYON_NUM_THREADS=1` before the
command for the one thread number and both unset for the many thread
one:

```text
cargo bench --bench pca_vars -- /Users/jose/devel/popnei-bench/big.vars \
    --runs 5 --num-prin-comps 0
```

The correctness checks of the `coding` skill run before any timing is
looked at, and the two tests that pin the numbers are the one that
compares the result over blocks of different sizes within 1e-10 and the
one that compares the rows read on threads with the rows read one after
another, bit for bit.

## The findings

### H1. The ploidy is a run time value, so the pass that writes the codes is scalar

`crates/popnei/src/pca.rs:1745`. Hot path, high confidence, found
independently by the hot loops reviewer and the numbers reviewer.

The loop walks the genotypes of a row with `chunks_exact(ploidy)`, and
the ploidy is a number the dataset carries, not a constant. The compiler
therefore vectorized the inner loop, over the two alleles of one
genotype, and left the outer one, over the thousand individuals, scalar:
the machine code has a path for 64 alleles at a time behind a test `cmp
x25, #64` and another for 8, and at a ploidy of 2 neither is taken. What
runs is nine instructions per allele plus fifteen per genotype. It is
54% of the instructions of a row.

With the chunk a compile time constant the same body becomes a
deinterleaving vector load: one reviewer compiled it in a scratch crate
and got 15 instructions per 16 genotypes against 34 per genotype, and
`chunks_exact(4)` gives the four allele version, so one constant covers
the ploidies 1 to 4 and the rest keeps the present loop.

The dosage is an exact count of alleles and the missing flag is a
boolean, so the two arms give the same bytes: **no result changes**. The
cost is a duplicated loop body behind a `match` on the ploidy and a test
that the two arms agree, which the tetraploid dataset the plan added
already exercises.

### H2. Finding the major allele is a scalar gather and a scatter

`crates/popnei/src/variant.rs:447`. Hot path, high confidence, found by
the hot loops reviewer, and the data layout and numbers reviewers
concur.

`count_alleles` walks the 2000 alleles of a row and, for each, loads,
increments and stores the entry of that allele in a table of 128 counts.
The address of the store is the value that was just read, which NEON
cannot do, and consecutive alleles hit the same entry, so the loop is a
chain of stores feeding loads. It is eleven instructions per allele and
34% of the instructions of a row. Two more sweeps of that table follow,
one to count how many alleles are distinct and one to find the largest
count, 1800 instructions more that do not depend on the number of
individuals at all.

The analysis needs three things of it: whether any allele was called,
how many distinct alleles there are, and which is the major one. When
every allele is the missing one, 0 or 1, which is what a biallelic
dataset is, all three follow from a count of the zeros and a count of
the ones, and that is the comparison and addition shape the compiler
already vectorizes elsewhere in this same file, 64 alleles at a time. A
row with an allele outside that range keeps the present loop, which is
also what still raises the errors of a variant with more than two
alleles.

The counts are integers, so **no result changes**. The cost is a second
counting function and the invariant that the fast path holds only for
alleles in that range, plus the fallback that has to stay tested.

### H3. The finiteness scans read 44 MB per block that the caller already knows about

`crates/popnei-linalg/src/lib.rs:195` and `:244`. Hot path, high
confidence, found by the linear algebra reviewer, and the concurrency
and data layout reviewers concur.

Before every product the crate walks every value of the standardized
block, 40 MB, and the lower half of G, 4 MB, to refuse a value that is
not finite. It is 1.68 ms of a call of 12.05 ms, 0.034 s of the run, and
it is a full round trip to main memory for data the standardizing has
just written and that fits in no cache.

Every value of that block was written from a table of at most `ploidy +
1` entries, which the standardizing fills. So the same question is
answered by three comparisons per variant instead of a thousand. The
measurement plan gates on the count of values scanned per block, five
million against three per variant, before any wall time.

**No result changes**: the same set of matrices is accepted and refused.
The cost is that "Errors" of `docs/specs/linalg.md` asks for those scans,
so the spec changes with the code, and something has to carry the
promise that the caller checked. A type that means "already checked" is
the shape, with no `unsafe`.

Beside it, and cheaper: both scans are written with a branch per value
and compile to one `f64` per iteration. A branchless form over eight
lanes compiles to vector loads, which the same reviewer verified. With
H3 taken only the scan of G is left, worth about 0.15 ms per block, so
this is the fallback if H3 turns out to cost more in the spec than it
gives.

### H4. The second pass reads and re-derives everything

`crates/popnei/src/pca.rs:613`. Hot path, medium-high confidence, found
by the data layout reviewer, with the input and output and hot loops
reviewers concurring.

Asking for the weights of 10 components, which is the default, costs
0.552 s on top of the 0.801 s: the file is read again and every block is
standardized again. What the second pass actually needs is the code of
each genotype, which is two bits, and the mean and deviation of each
variant, sixteen bytes. At this size that is 25 MB packed against a
process that holds 0.21 GB; at the largest dataset of the objectives it
is 2.5 GB, so it has to be conditional on a budget.

**No result changes** if the kept codes and scales are the ones the
first pass computed. The cost is a buffer with a size policy, an error
when it does not fit, a second path through the second pass, and the
loss of the check that the two passes saw the same variants, which
exists today and would become meaningless.

### H5. Nothing is read while a block is being used

`crates/popnei/src/pca.rs:849`. Hot path for the many thread run,
high confidence, found by the concurrency reviewer and the input and
output reviewer independently.

The loop reads a block, then uses it, on one thread. Section 3 of
`docs/architecture.md` describes a read ahead thread between a reader
and its consumer, one block ahead; the spec of the vars file defers it
to "the first calculation that consumes blocks", and this analysis is
that calculation, and it was not built. The read is 5.3 ms against 33 ms
of work per block at one thread, so it hides entirely; at 18 threads the
work falls and the read does not, and the reading is then 0.107 s of the
0.352 s, 30% of the run.

**No result changes** while the blocks keep the order of the file, since
G is a sum over them in that order. The cost is a thread and a channel
of one block in a crate that has neither outside the reader of bgzip, 10
MB more alive, a serial path under wasm, and the fact that "0.3 s on one
thread" stops meaning one thread.

### Likely

- **The scratch of a row is built once per rayon job, not once per
  thread**, `crates/popnei/src/pca.rs:1020`. The allocations reviewer
  counted about 2600 of them per block at 18 threads on a replica of the
  same chain, each one an allocation and 3.6 KB zeroed, about 12 MB per
  block. One call setting a minimum length of the split fixes it. It
  cannot help the one thread number, where there are eight per block.
- **pandas copies every array the analysis returns**, `python/popnei/pca.py:251`.
  Measured by the Python boundary reviewer on this interpreter: the frame
  does not share memory with the array, and at 10000 individuals building
  it costs 1.6 GB of peak memory against 2 MB with one keyword. At 1000
  individuals it is 8 MB and part of the 22 ms the whole boundary costs.
  The keyword is `copy=False` at six places, and the invariant is that
  the array has no other owner, which holds because it comes straight
  from Rust.
- **The table of 128 allele counts is swept three times a row whatever
  the variant holds**, about 1940 instructions that do not depend on the
  individuals. Largely subsumed by H2, which removes the sweeps for a
  biallelic row; worth its own line only for the fallback path and for
  datasets of very few individuals, where it is about half the cost of
  counting.
- **A fresh 10 MB buffer is allocated and the genotypes copied into it
  for every block**, `crates/popnei/src/io/vars.rs:2371`. arrow owns that
  memory as a plain vector and can hand it over. 200 MB of copying per
  pass. The cost is a chain of conversions with a fallback that has to
  stay tested.

### Speculative

- **Every batch of the file is filled with zeros before it is read
  over**, `crates/popnei/src/io/vars.rs:2771`, 81 MB per pass, which two
  reviewers found independently and one saw in the machine code as a call
  to `bzero`. Reading into the spare capacity instead avoids it. Worth 2
  ms or nothing.
- **The result of a row crosses as 64 bytes to carry one bit**,
  `crates/popnei/src/pca.rs:1016`, because the error type is large and
  travels in the success type. 320 KB per block against 40 MB of writes.

### For the owner

- **The block of 5 million genotypes is pyNei's number and nobody has
  measured it for popnei.** Changing it changes the order in which G is
  summed and so the last bits of a published result, which is why it is
  yours. Two reviewers bound the gain at about 1% either way by
  arithmetic on measured memory rates, and the experiment costs a sweep
  of five sizes, with the trap that the file's batches are 5000 variants,
  so any other size makes the reader cut and copy and the sweep measures
  the copy unless the file is rewritten at each size.
- **The vars file is compressed with lz4, and the decompression is
  essentially the whole read cost.** "The compression" of
  `docs/specs/io_vars.md` measured the same genotypes at 19 ms
  compressed and 1 ms uncompressed, on a file 2.6 times larger. The
  format chose lz4 over zstd on build grounds, not read speed, and never
  compared with no compression at all. Offering a vars file without
  compression is a format decision, and at the largest dataset of the
  objectives it is 20 GB against 8 GB on disc.
- **The eigendecomposition computes every eigenvector so that ten can be
  used.** The routine that computes a chosen range took 0.025 s, 0.18 s
  and 4.9 s at 1000, 2000 and 5000 individuals against 0.035 s, 0.27 s
  and 6.3 s, and needs 26n floats of workspace instead of 2n², which at
  10000 individuals is the difference between 2.4 GB and 0.8 GB of peak
  memory. It is cold at 1000 individuals, 3% of the run, and it is what
  the analysis is made of at the top of the objectives' sizes. It is
  tied to Open 1 of `docs/specs/pca.md`, which is yours, and faer has no
  such routine, so the two backends would stop computing the same set of
  components.
- **No toolchain is pinned.** Every baseline in this report and in the
  measurement report is against an unpinned rustc 1.98.0, and what the
  compiler vectorizes changes between versions with no change in the
  code. A `rust-toolchain.toml` would make the baselines mean something
  next month.

## Seen outside the scope

- **No test compares the whole analysis at one thread with several.**
  The test that exists compares the rows of a block, which stops before
  G, and it reads rayon's global pool rather than setting a thread count,
  so under one thread it compares one thread with itself. The threads of
  the product come from a variable read when the process starts, which
  popnei cannot set. This is a gap of the tests and not of the
  performance; it belongs to a code review, and the filters module has
  the test to copy.
- The tolerance of the test that compares block sizes is absolute, on a
  matrix whose entries are of order 1 in the fixture and of order 1e5 at
  the sizes that are timed, so it pins nothing about a relative error at
  scale.
- The checklist of this skill says the vars file is compressed with
  zstd; it is lz4.

## What the code already does well

- **The row is cut so that nothing is shared between threads.** Each row
  of the output is its own slice, the inputs are read only, and there is
  no atomic, no lock and no channel anywhere on the path. The
  concurrency reviewer found nothing to pad and nothing to unnest: the
  products are taken outside the parallel section, as the architecture
  requires.
- **The buffers are allocated once and reused.** G is allocated at its
  final size and handed to the eigendecomposition by value, which turns
  it into the eigenvectors with no copy; the block's buffer is allocated
  once per pass; the weights are written into their columns with no whole
  matrix copy. The claim that nothing is allocated per variant holds.
- **The counters of one byte in runs of 255 are already the right
  shape.** The numbers reviewer replaced them with a wider counter and
  the compiler produced 117 instructions more, because the wide form
  loses the instruction that adds four bytes at a time. 255 is the
  longest run a byte can count, and it is used.

## What the experiments showed

Each entry has the two measurements, the dataset and the machine, and
ends in one of: applied, with the commit; no gain, closed; not run, with
the reason; or for the owner.

### The apparatus, and what it changed about the plan

At 82472ba a benchmark times the four passes over a row on their own,
through a cargo feature of the core crate that is off by default, and at
56a7545 a build profile keeps the debug information of a release build,
which was checked to give the same 1664 instructions for the closure and
the same listing line for line.

The baseline, one block of 5000 variants of 1000 individuals of
`big.vars`, one thread, the best of five runs, run by the orchestrator
with nothing else building:

| pass over the rows of the block | best | median | share |
|---|---|---|---|
| the counts of the alleles | 13.797 ms | 13.827 ms | 69.5 |
| the codes of the genotypes | 4.221 ms | 4.295 ms | 21.3 |
| the values of the codes | 0.834 ms | 0.837 ms | 4.2 |
| the counts of the codes | 0.392 ms | 0.392 ms | 2.0 |
| a whole standardized row | 19.849 ms | 19.995 ms | |

The four come to 19.244 ms of the 19.849 ms, 97 per 100, which is the
gate the benchmark was built to pass, and the whole row at 19.8 ms is
the 20.6 ms per block the sampling profile gave.

**The ranking of this review was wrong, and the measurement is what
says so.** The instruction counts put the writing of the codes at 54 per
100 of a row and the counting of the alleles at 34; the times put the
counting of the alleles at 69 per 100 and the writing of the codes at
21. The reason is in the mechanism that H2 already describes: the
counting loads, increments and stores the same entry of a table for
consecutive alleles, so each iteration waits for the one before it,
while the writing of the codes, scalar as it is, has no such chain. An
instruction count says how much work there is and not how long it takes.
So H2 is the first experiment and H1 the second, and the review's own
order is corrected here rather than in the findings, which are left as
they were written.

A note for every later experiment: the whole row moved by 5 per 100
between two invocations of the same command, 19.849 ms and 20.915 ms,
where five runs inside one invocation spread by 1 per 100. A difference
under about 5 per 100 is confirmed with a second clean measurement of
each side, as this skill asks.

### H2, counting the alleles: applied at e6db676

The counting of the alleles of a variant no longer walks its 2000
alleles into a table of 128 counts. A variant whose alleles are only the
missing one, 0 and 1 is counted by counting its zeros, its ones and its
missing alleles, which the compiler turns into 64 alleles per iteration,
four vector loads compared against each of the three values and added
into the counters. The three counts come to the alleles of the variant
exactly when it holds no other, so the one test both counts and says
whether the fast way was allowed; a variant of more alleles falls back
to the old loop, having paid 0.57 ms per 10 million alleles for the
attempt.

The change went inside `count_alleles` rather than beside it, so every
caller gets it: the filter by missing data, which also counts alleles,
gains the same, and no second public function has to be kept tested.

| | before | after |
|---|---|---|
| counting the alleles of a block of 5000 x 1000 | 13.807 ms | 0.568 ms |
| a whole standardized row of that block | 19.742 ms | 6.867 ms |
| the analysis of 100000 variants x 1000 individuals | 0.784 s | 0.532 s |

The best of five runs inside one invocation, one thread, on the owner's
Apple M5 Pro with nothing else building, taken by the subagent that made
the change; the orchestrator ran the analysis again afterwards and got
0.533 s at best and 0.534 s as the median against the 0.795 s it had
measured at the baseline. The difference is 32 per 100 of the analysis,
far above the 5 per 100 the same command varies by, so no revert was
needed to confirm it.

The numbers did not move: the checksums of the benchmark are the same on
both sides, the first component holds 6.228 per 100 of the variance as
before, and `cargo test --workspace` gives 353 tests and 33, all
passing, one more than at the baseline, which is the test of the new
path.

What it cost: thirty lines of a second way to count and the invariant
that it holds only for those three allele values.

One thing the experiment could not explain: the pass that writes the
codes, which the change does not touch, read 4.119 ms before and 4.717
ms after, 14 per 100 more. It is where the compiler put the code, and it
is inside the 0.252 s the analysis gained.

### H1, the length of a genotype as a constant: applied at ff21868

The pass that writes the dosage of each genotype now has the length of a
genotype written into the code for the ploidies 1 to 4, through one
function with a constant length and a match on the ploidy; every other
ploidy keeps the loop that reads the length from the dataset. The
machine code changed as the finding predicted: before it, no
deinterleaving load anywhere in the row, and the loop over the alleles
of one genotype vectorized behind tests for 64 and for 8 alleles that a
ploidy of 2 never takes; after it, a main loop of 15 instructions for 16
genotypes on a pair of vector registers, with an eight genotype form and
a scalar tail.

| | before | after |
|---|---|---|
| writing the codes of a block of 5000 x 1000 | 4.420 ms | 0.325 ms |
| a whole standardized row of that block | 6.710 ms | 3.010 ms |
| the analysis of 100000 variants x 1000 individuals | 0.522 s | 0.437 s |

The best of five runs inside one invocation, one thread, on the owner's
Apple M5 Pro with nothing else building. The orchestrator ran the
analysis again afterwards and got 0.443 s at best and 0.447 s as the
median. The difference is 16 per 100, above the 5 per 100 the same
command varies by.

The numbers did not move: the checksums of the benchmark are identical
on both sides and the first component holds 6.228 per 100 of the
variance. `cargo test --workspace` gives 355 tests and 33, two more than
before, which are the two the change came with: the codes of a genotype
of 1 to 5 alleles against literals, which reaches every arm of the
match, and the codes at the ploidies 1 to 4 over 131 individuals against
the loop that reads the ploidy.

What it cost: the body of the loop exists twice, about 35 lines, and the
match gains an arm if a ploidy above 4 is ever worth it.

### Where the analysis stands after the two experiments

| | at the baseline | now |
|---|---|---|
| the analysis, one thread, no weights | 0.795 s | 0.443 s |
| a standardized row of a block of 5000 x 1000 | 19.849 ms | 3.010 ms |

44 per 100 of the analysis is gone and the standardizing, which was
51.6 per 100 of it and the reason for this review, is now about 0.06 s
of 0.443 s. The target of 0.3 s is 0.143 s away, and what is left is the
product of the blocks, 0.254 s, of which the two finiteness scans are
0.034 s; the reading of the file, 0.107 s, which is the compression and
is the owner's; and the eigendecomposition, 0.024 s. Both experiments
left every number of every result where it was.

A curiosity neither experiment explains: after each change, passes that
the change does not touch read 10 to 30 per 100 slower in the per pass
benchmark, while the whole row falls by much more. It is where the
compiler places the code, and it is inside the gains.

### H3, the first half, the scans vectorized: applied at e64637c

The two scans for a value that is not finite are written so that the
compiler vectorizes them: one function that all four call sites use,
whose loop reads eight values a turn in four pairs of vector registers
and tests them with no branch on a value, the values left over at the
end keeping the scalar test. Before it, each scan read one value per
iteration with a conditional branch.

| | before | after |
|---|---|---|
| the analysis, no weights | 0.439 s | 0.426 s |
| the analysis, the weights of 10 components | 0.633 s | 0.612 s |

Each side was measured in two invocations of five runs, and the baseline
a third time after the change was reverted and rebuilt; every
measurement with the change is below every measurement without it, and
the spread inside a side is 0.001 s against a gap of 0.013 s. The
orchestrator measured 0.426 s afterwards. The gain is 3 per 100, which
is small, and it is apart from the noise, which on this benchmark is far
tighter than the 5 per 100 seen between invocations earlier: three
separate invocations of the baseline all gave 0.439 s.

The numbers did not move, and both backends were run: 355 tests of the
workspace, 35 of the linear algebra crate, and 30 of the same crate with
the BLAS feature off, which is the faer backend.

Two tests came with it, and why says something about the tests that were
there: the four that existed use matrices of 6 and 9 values, fewer than
the eight of one turn of the new loop, so they reached only the values
left over at the end. The new two put a value that is not finite in
every place of a matrix of 2 x 12 and of a 12 x 12, and both fail when
the loop is broken.

**What this settles about the other half of H3.** The scans were 0.034 s
of the analysis and this recovered 0.013 s of them. Letting the caller
vouch that it has already checked would take at most the 0.021 s that is
left, under 5 per 100 of the analysis, and only the part of it that is
the block: the scan of the individuals matrix stays whatever the caller
promises. For that it would change "Errors" of `docs/specs/linalg.md`
and add a type that carries the promise across the crates. **Not run:
the gain does not justify the spec change.** What the branch removal

### The copies pandas made: applied at 8db746e

Each of the six frames and series that the two Python functions build
now says that it must not copy the array the binding handed it. Before
the change no frame shared memory with its array; after it every one
does, through both public functions.

| building the three frames of an analysis of 10000 individuals | before | after |
|---|---|---|
| peak resident memory | 1721 MB | 913 MB |

The arrays alone are 910 MB, so what the frames added fell from 811 MB
to 3 MB. At the size of the benchmarks of this review the copy is 8 MB
and the wall time does not move, 0.613 s against 0.615 s, which is what
was expected: this is a memory finding and not a speed one, and it
matters at the sizes the objectives name and not at the ones that were
timed.

The invariant the change needs is that nothing else holds the array,
which is true because it comes straight from Rust and only the frame
survives the call; the code says so where it relies on it. 208 pytest
tests pass.
