# The numbers stay right

**Purpose.** popnei's first goal is to be right, and speed is the fourth. An optimization that moves a result outside the tolerance of its spec, or makes it depend on the number of threads, is a defect, however fast it is. This checklist is read for every proposal that touches arithmetic, and by the orchestrator before any experiment is kept.

**Triggers.** Any finding or proposal that reorders, parallelizes or vectorizes a float reduction; changes a chunk or block size; replaces a maths function; changes an integer type or a cast; changes the build profile; or packs the genotypes differently.

**Skip when.** The scope has no arithmetic whose result reaches the user: I/O buffering, allocation of scratch space, the layout of a struct that holds no numbers.

## Rules

- **The tolerance is the spec's, not the reviewer's.** Each calculation has a spec under `docs/specs/` that says how it is compared: exactly, for counts and sets of variants, or within a tolerance that has a reason, usually the digits the reference program prints. A proposal names that tolerance and its measurement plan reruns the tests that assert it.
- **No result depends on the number of threads.** A float total whose parts are joined in an order rayon chooses at run time changes its last bits with the pool. The fix the `coding` skill gives is chunks of a fixed size, partial results collected in index order and added serially. A proposal that parallelizes a float reduction includes the test that runs it at one thread and at several over data that spans several chunks, and compares the results as equal, not as close.
- **Between platforms, within the tolerance and no more.** The owner decided in September 2026 that popnei does not promise the same bits on macOS, Linux and wasm. So reassociation that depends on the vector width of the target, `algebraic_add` and its family, is allowed where the tolerance holds. A global fast-math flag is not, because it also licenses assumptions about NaN and infinity, and popnei's missing values become NaN at the Python boundary.
- **`mul_add` is not a free win.** It rounds once where `a * b + c` rounds twice, so it changes the result, and R and plink2 compute the two-step form. Propose it only where the spec's tolerance is wide enough, and say so. Under `wasm32-unknown-emscripten` it compiles to a call to a software `fma`, where the two-step form is `f64.mul; f64.add`, so in the browser it is slower as well.
- **A value that is exact stays exact.** A monomorphic variant has an expected heterozygosity of exactly 0.0, a frequency of exactly 1.0, and such values sit on the edge of a histogram bin, where one unit in the last place moves a count that the spec compares as equal. Replacing a division by a multiplication with the reciprocal is the usual way to lose this: for 5194 of the first 40000 integers c, `c * (1.0 / c)` is not 1.0, the first being 49. A proposal that touches a division says what it does to the exact cases.
- **`powi` with an exponent known only at run time is a call, not a loop.** `a.powi(k)` with a runtime `k` compiles to an out-of-line `__powidf2`, and above k = 2 it differs from repeated multiplication in the last place. When one exponent is the common case, the ploidy 2, an arm for it outside the loop is both faster and bit identical.
- **`f32` for speed is a change of the result.** Halving the width of a float array halves its memory traffic and doubles the SIMD lanes, and it loses nine digits. It is a proposal for the owner, with the error against the reference measured, not a finding to apply.
- **Integer widths follow the `coding` skill.** A `u32` count is faster to vectorize than a `u64`, and a count that runs over the whole dataset does not fit in it: a million variants of 10000 samples are 1e10 genotypes. The per variant count in a narrow type with a stated bound, added once into a `u64` total, is the shape that is both fast and right.
- **Checked arithmetic in a hot loop is measured before it is removed.** The `coding` skill asks for `checked_` operations unless a bound makes overflow impossible. A proposal to replace them states the bound, shows where it is established, and shows with a benchmark that the checked version was the cost. What the checks cost in the allele counting is not known: the one timing there is, on the trial crate of September 2026, 373/351/347 ms with the per-call checks against 357/317/360 ms without over 3000000 calls, three runs a side with overlapping ranges and minima 9% apart, cannot tell "free" from "about 9%", and its harness was not kept.
- **The correctness tests are part of every experiment.** `cargo test --workspace`, and the pytest tests that compare with pyNei once that layer exists, run after the change and before the timing is looked at. A faster wrong answer is not a result.
